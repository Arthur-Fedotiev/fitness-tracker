# Flatten `Exercise.baseData` into top-level fields

`exercises/{id}` documents still wrap their content in a `baseData` object (`name`, `exerciseType`, `targetMuscle`, `equipment`, `instructions`, `userId`, `admin`) — the last surviving nesting layer from the old translation pipeline; `translatableData` itself was already fully removed from code by [ADR-0002](0002-remove-multilanguage-support.md). Everything above the Firestore boundary (`shared-package`'s `Exercise` interface, domain state, UI) already treats an exercise as flat; `baseData` only shows up in `exercise.data.service.ts`, its DTOs, `ExerciseResponseModel`'s constructor, and `firestore.rules`, each unwrapping or re-wrapping it a few lines from the read/write call. We're dropping the wrapper so the shape matches everywhere.

Migration is an in-place transform (a `firebase-admin` script doing a full `.set(ref, flatData)` replace per document, same doc IDs, run staging then prod) rather than regenerating the collection. Workouts reference exercises by document ID (`content[].id`, including nested Superset composites), and a regenerated collection would either mint new IDs and dangle every workout, or require hand-reconciling admin-owned vs. user-created exercises on the way back in — the in-place script does neither. A read-only survey (`functions/scripts/lib/survey-exercise-flatten-readiness.ts`) confirmed, against both `fitness-tracker-ui-dev` (31 exercises) and `fitness-tracker-de06b` (128 exercises), zero missing `baseData` and zero dangling workout→exercise refs before committing to this approach.

The same survey found every document in both environments still carries dead fields never cleaned up by [ADR-0001](0001-drop-exercise-media.md) and ADR-0002 — top-level `translatableData`/`translatedData`, and inside `baseData`: `avatarUrl`, `avatarSecondaryUrl`, `coverUrl`, `coverSecondaryUrl`, `instructionVideo`, `muscleDiagramUrl`, `rating`, and on some docs a duplicate `id` key. The full-replace write scrubs all of it as a side effect of flattening, not a separate cleanup pass.

Since `firebase-admin` bypasses Firestore rules, the migration script can run before `firestore.rules` or the app code changes. The rules and app-code updates land together right after. We accepted the resulting short broken-app window (single-user personal app, timed at will) rather than add a transitional `data.baseData ?? data` dual-read path to the data service — a temporary abstraction for a capability (zero-downtime migration) this app doesn't need.

## Consequences

- `firestore.rules`'s ownership helpers (`isRequestOwnershipValid`, `isPublicResource`, `isOwnedByUser`, `isAdminResource`) collapse from a `type == 'workout' ? data.admin : data.baseData.admin` branch to one shape-agnostic path, now that `workout` and `exercise` documents both carry `admin`/`userId` at the top level.
- `functions/scripts/lib/update-exercise-ownership.ts` retires (same fate as the four scripts [ADR-0003](0003-prune-dependencies-and-retire-completed-migrations.md) already retired) — the survey confirms every document in both environments already has `userId`/`admin` set, so its job is done.
- `EXERCISE_FIELD_NAMES.RATING` and the proficiency-level field (offered by `exercise-descriptors`, never persisted) are known-dead but deliberately untouched by this change — don't fold their removal into this migration's diff.
- Enriching the exercise library (more/better content) is explicitly a separate, later, additive project — new `admin: true` documents on this now-flat schema — not part of this migration.
