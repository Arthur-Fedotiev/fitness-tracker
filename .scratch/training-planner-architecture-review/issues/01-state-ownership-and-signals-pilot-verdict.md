## Question

`program.store.ts` is the repo's first `@ngrx/signals` pilot (`exercise`/`workout` still use classic NgRx). Meanwhile `program-dashboard.component.ts` carries a pile of its own local signals alongside it: `selectedProgramId`, `activeStatus`, `activeEditSession`, `blockValidity` (a `Record<string, boolean>` keyed by block id), plus computed signals (`selectedProgram`, `readOnly`, `saveDisabled`, `livePersistedProgram`) that branch on combinations of that local state and the store's `draftProgram`/`programs`/`dirty`. There's also a constructor `effect()` that auto-begins an edit session for Draft Programs by reading both `livePersistedProgram()` and `store.draftProgram()`.

Take a critical, from-scratch look (clean read of the current code, not anchored to a specific bug) at:

1. **Is `@ngrx/signals` working well here** — does its shape (plain `async`/`await` methods, no Observables/Effects, `patchState`) fit this feature, or is it fighting the problem?
2. **Where should the state-ownership line sit** between `ProgramStore` and `program-dashboard.component.ts`? Specifically judge `selectedProgramId`, `activeStatus`, `activeEditSession`, and `blockValidity` — could/should any of these live in the store to make the component leaner, or does keeping them component-local (since they're UI-only concerns like "which tab is showing," not persisted data) actually make more sense than the alternative?
3. **Don't presuppose state has to move.** The user likes reactive/unidirectional (Redux-style) patterns and isn't grading this on "less local state is always better" — grade each piece of state on whether it's pulling its weight where it currently lives. "Keep the current split, it's fine" is a legitimate verdict.

This ticket blocks the dialog-consolidation ([[02-consolidate-scattered-dialog-logic]]) and effects-consistency ([[03-state-change-and-side-effect-consistency]]) tickets, since `guardLeavingSession()` — the dialog-opening logic — sits right at the boundary this ticket is judging, and moving state could reshape where that logic lives.

## Answer

**1. Is `@ngrx/signals` working well here?** Yes — keep the store's shape as-is. Plain `async`/`await` + `patchState`, no Observables/Effects, fits cleanly: Firestore I/O here is one-shot (confirmed by [strength-reload-calculator ticket 08](../../strength-reload-calculator/issues/08-real-implementation-architecture.md), no realtime listener anywhere in this codebase), so there's nothing being fought. `computed()` mixing store signals with component-local signals in `program-dashboard.component.ts` is idiomatic, not a smell.

Separately raised and confirmed viable: `@ngrx/signals/events` (`withReducer`/`withEffects` — a genuine Redux-style events/reducer/effect layer, visible in Redux DevTools, which is already wired app-wide via `provideStoreDevtools` in `libs/shared/data-access/src/lib/+state/provide-shared-state.ts` for the classic-NgRx `exercise`/`workout` domains but currently blind to `ProgramStore`'s plain `patchState` calls) is **already installed** — `@ngrx/signals@21.1.1`'s `./events` subpath exists in `node_modules` today, no upgrade needed. Not adopted in this pass; logged as fog on the map, to revisit after MVP release.

**2. Where should the ownership line sit?**

- **`selectedProgramId`** — moves into `ProgramStore` (new `selectProgram(programId)` method). Today it's a component signal synchronized to the store's `draftProgram` via a constructor `effect()` + `untracked()` that imperatively calls `store.beginEditSession()` whenever a Draft becomes selected — a two-hop watch-then-react flow standing in for what's really a single event ("user selected this program"). Moving it collapses that into one direct store call from the click handlers that already know the selection changed (`onCreateProgram`, `onSelectProgram`), deleting the effect entirely.
- **`activeEditSession`** — moves into `ProgramStore` too (as a `sessionActive`-shaped field, flipped by `beginEditSession`/`cancelEditSession`/`saveProgram`). Originally judged as a legitimate local flag because Draft/Active/Completed were asymmetric (see point 3 below) — a separate flag was needed because `cancelEditSession()` deliberately doesn't null `draftProgram`, so draft-existence alone can't signal "is editing." Once that asymmetry is removed, the store already owns the full begin/cancel/save lifecycle, and keeping this split is the same "component reconstructing what the store already knows" issue that motivated moving `selectedProgramId`. `readOnly`/`selectedProgram` computeds simplify to drop their `status === 'draft'` special-casing.
- **`activeStatus`** — stays component-local. Pure tab-UI state; confirmed there's no route/query-param home for it either (the Training Planner route is flat, no children, no params — `libs/program/shell/src/lib/program.routes.ts`).
- **`blockValidity`** — stays component-local; form validity is not domain state. Gets a one-line fix: reset to `{}` at session-boundary transitions (program select/create/start-edit/cancel-edit) — confirmed via grep it's never pruned today, so it grows unbounded across the app session (functionally harmless — `saveDisabled` only reads keys for the current program's blocks — but worth the one-line fix). A `FormArray`-based alternative (letting Angular aggregate child-form validity natively) was considered and rejected: each `MainLiftBlockFormComponent` is deliberately self-contained (owns its own `FormBuilder` group, rehydrates from a plain `block` input, talks only via outputs) for independent testability, matching where the single-file-component convention ([[04-single-file-component-convention]]) is headed; a `FormArray` would make the parent structurally synchronize an array of `FormGroup`s against the staged `mainLiftBlocks` array on every add/remove for a win the prune fix already buys more cheaply.
- **`sessionEpoch`** — confirmed pulling its weight (verified via grep: consumed by `main-lift-block-card.component.ts` to reset its `stale` flag on session boundaries). No change.

**3. Behavior change surfaced during resolution:** Draft Programs lose their implicit always-in-session editing. Every status (Draft/Active/Completed) now requires an explicit "Start Editing" click — except immediately after creation, where `onCreateProgram` auto-starts the session in the same handler (creating a Program is an unambiguous "edit this now" signal, and the handler already sets the selection there). This is what actually removes the asymmetry that justified keeping `activeEditSession` local in point 2 — `program-edit-toggle.component.ts` needs no structural change (it's already driven purely by `readOnly`/`startEdit`/`save`/`cancelEditing`, confirmed by reading its template usage), just a stale doc comment fix ("Draft Programs are always editable and never render this" no longer holds).

**4. Status-tab optimistic switching** (`onStatusTabChange`'s set-then-revert-on-block pattern) — left as-is. Traced the reason it exists: `MatTabGroup` mutates its own visual tab selection synchronously on click, independent of `activeStatus`; going "check first" with no optimistic set would leave the tab header visually stuck on the just-clicked tab when the guard blocks (Angular's one-way `[selectedIndex]` binding has no diff to push), reintroducing the exact bug the current code was written to avoid. Not worth the larger change (intercepting the click before `MatTabGroup`'s own internal selection updates) to remove a Material-forced implementation detail.

**5. Explicitly deferred, not decided here:** a reusable abstraction for the repeated "guard, then branch" shape across `onCreateProgram`/`onSelectProgram`/`onStatusTabChange`/`confirmLeave` — squarely [[02-consolidate-scattered-dialog-logic]] and [[03-state-change-and-side-effect-consistency]]'s job. Hard constraint those tickets must carry forward: `libs/program/domain` is Nx-tagged `type:domain-logic`, `libs/program/ui` (home of `DiscardChangesDialogComponent`) is tagged `type:ui`; `.eslintrc.json`'s `@nx/enforce-module-boundaries` forbids `type:domain-logic` → `type:ui` entirely (verified in `.eslintrc.json:54-55`). So `ProgramStore` can never open that dialog itself — it can own `dirty()`-style predicates and transition methods, but the confirm-dialog step must stay in `program/feature-dashboard` or a shared UI-layer service.
