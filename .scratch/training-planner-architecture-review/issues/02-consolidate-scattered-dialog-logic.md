## Question

Confirmation-dialog handling is split across three call-sites with two different patterns:

- `libs/program/ui/src/lib/program-delete-button/program-delete-button.component.ts` uses the generic, repo-standard `ConfirmationDialogService` (from `@fitness-tracker/shared/ui/components`) — a binary confirm/cancel dialog, RxJS-based (`.pipe(takeUntilDestroyed()).subscribe(...)`).
- `libs/program/feature-dashboard/src/lib/program-dashboard.component.ts`'s `guardLeavingSession()` opens `DiscardChangesDialogComponent` directly via `inject(MatDialog)`, wrapped in `firstValueFrom(...)` for `async`/`await` use, handling a three-way result (`'save' | 'discard' | undefined`).
- `libs/program/ui/src/lib/program-edit-toggle/program-edit-toggle.component.ts`'s `onCancelClick()` opens the *same* `DiscardChangesDialogComponent` again, independently, via its own `inject(MatDialog)` + `.afterClosed().subscribe(...)`, handling a two-way result (`'discard' | undefined` — no save option in this caller).

Both `DiscardChangesDialogComponent` call-sites duplicate the `MatDialog.open(...)` config shape and hand-roll their own result-branching, one Promise-style and one Observable-style, for what is conceptually the same "confirm before discarding" action.

Decide: should this consolidate into one shared abstraction — e.g. extending `ConfirmationDialogService` to support a three-way save/discard/cancel result so all three call-sites share one service, or a new small dedicated service/helper wrapping `DiscardChangesDialogComponent` specifically, used by both its callers, left separate from `ConfirmationDialogService`'s binary case? Pick a direction and produce a ready-for-agent implementation ticket (or do the edit directly if trivial enough once decided).

Depends on [[01-state-ownership-and-signals-pilot-verdict]]: if that ticket moves `activeEditSession`/session-guard logic into the store, the natural home for the consolidated dialog call may shift with it.

## Answer

Two of the three call-sites consolidate; `ProgramDeleteButtonComponent` is untouched.

- **`ConfirmationDialogService` stays as-is, not extended.** It's genuinely cross-domain — `libs/workout/feature-compose-workout/src/lib/compose-workout/compose-workout.component.ts` uses the same binary service for its own "remove exercise" confirm (verified via grep). Widening its contract to a three-way save/discard/cancel result to fit Program's case would reshape a shared, cross-domain component around one domain's needs — the map explicitly rules cross-domain dialog auditing out of scope. `ProgramDeleteButtonComponent`'s call-site needs no change.
- **The two `DiscardChangesDialogComponent` call-sites** (`program-edit-toggle.component.ts`'s `onCancelClick()`, `program-dashboard.component.ts`'s `guardLeavingSession()`) **consolidate into a new `DiscardChangesDialogService`**, co-located at `libs/program/ui/src/lib/discard-changes-dialog/discard-changes-dialog.service.ts` next to the component it wraps (mirrors `ConfirmationDialogService`'s own co-location precedent), exported from `program/ui`'s public-api alongside the existing `DiscardChangesDialogComponent`/`DiscardChangesDialogResult` exports. Module boundaries allow this: `program/feature-dashboard` is `type:feature`, permitted to depend on `type:ui`.
- **Shape**: a single method, `confirm(data: DiscardChangesDialogData): Observable<DiscardChangesDialogResult>` — mirrors the dialog's existing `saveLabel`-optional data contract to cover both the 2-way (edit-toggle) and 3-way (dashboard) cases, rather than two differently-named methods.
- **Observable, not Promise.** Matches `ConfirmationDialogService`'s convention and the user's RxJS-first preference (carried from ticket 01). `program-edit-toggle.component.ts` keeps subscribing directly, unchanged in style. `program-dashboard.component.ts`'s `guardLeavingSession()` keeps converting via `firstValueFrom` at its existing boundary — **unchanged from today**. Explicitly decided *not* to rebuild `guardLeavingSession` as an RxJS pipeline or switch `confirmLeave()`'s `CanDeactivate` entry to `Observable<boolean>` in this ticket, even though RxJS pipelines can cleanly wrap the promise-based `store.saveProgram()`/`store.cancelEditSession()` calls via `from(...)` — [[03-state-change-and-side-effect-consistency]] already explicitly owns "the guard-then-branch shape... factored into something less repetitive" across `onCreateProgram`/`onSelectProgram`/`onStatusTabChange`/`confirmLeave`, and should judge that against the code this ticket leaves behind, not preempt it.
- **Thin wrapper only.** The service replaces the duplicated `MatDialog.open(...)` config and the two different consumption styles — it does not take callbacks or drive store mutation itself. Each caller still branches on the returned result (`'save' | 'discard' | undefined`) and calls its own store methods. Matches the ticket-01 standing lens: state and behavior should live where they pull their weight, not be minimized/centralized for its own sake — the two callers react differently enough (2-way vs 3-way, different post-actions) that a callback-driven service would just be an ad hoc controller.
- **The dirty-check short-circuit stays at each call-site** (`if (!this.dirty())` / `if (!this.store.dirty())` before opening the dialog at all), not folded into the service — the two callers resolve "not dirty" differently (immediate `cancelEditing.emit()` vs immediate `return true`), so centralizing it would force a uniform skip shape onto the thin wrapper for no gain.

Produces a ready-for-agent implementation ticket: [Implement DiscardChangesDialogService consolidation](07-implement-discard-changes-dialog-service.md).
