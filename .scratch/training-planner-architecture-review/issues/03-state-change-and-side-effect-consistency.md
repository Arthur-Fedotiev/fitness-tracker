## Question

Side-effect handling mixes patterns within the same files:

- `libs/program/ui/src/lib/main-lift-block-form/main-lift-block-form.component.ts`'s constructor has *three* separate reactive registrations doing related work: an Angular `effect()` that rehydrates the form when `block()` changes, a `this.form.controls.manualOverride.valueChanges.pipe(takeUntilDestroyed()).subscribe(...)` for the manual-override toggle, a second `effect()` for the `readOnly()` enable/disable, and a third `this.form.valueChanges.pipe(takeUntilDestroyed()).subscribe(...)` that just emits `formChanged`. Signal-`effect()` and RxJS-`subscribe()` are doing the same *kind* of job (reacting to a change and pushing a side effect) side by side.
- `libs/program/feature-dashboard/src/lib/program-dashboard.component.ts` has its own constructor `effect()` (auto-begin edit session for Drafts) plus a `guardLeavingSession()` that's an imperative `async` method awaited from multiple click handlers (`onCreateProgram`, `onSelectProgram`, `onStatusTabChange`, `confirmLeave`), each repeating a similar "guard, then branch on the boolean" shape.
- `notify()` (a thin `MatSnackBar.open` wrapper) is called ad hoc from inside action handlers (`onDeleteProgram`, `onGenerate`, `saveProgram`) rather than through any consistent effect/notification pattern — easy to forget on a new action.

Decide what "consistent" should mean here: pick one idiom for reactive side effects (e.g., prefer `effect()` uniformly for signal-driven cases and reserve RxJS `subscribe` for genuinely stream-based cases like form `valueChanges`, or the reverse) and decide whether the guard-then-branch shape in the dashboard's click handlers should be factored into something less repetitive. Produce a ready-for-agent implementation ticket for whatever the audit concludes needs to change (may conclude some of this is fine as-is).

Depends on [[01-state-ownership-and-signals-pilot-verdict]]: its state-ownership verdict may relocate some of the effects being judged here (e.g. the dashboard's edit-session auto-begin `effect()`), so resolve that first.

## Answer

Judged against the post-06/post-07 code (`main-lift-block-form.component.ts` untouched by either; `program-dashboard.component.ts` reflecting both). No code changes — every point audited is fine as-is; only outcome is a new codebase-wide convention written to `CONTEXT.md`.

**1. Reactive-side-effect idiom (`main-lift-block-form.component.ts`).** Keep the existing split as-is: `effect()` reacts only to `@Input` signals (`block()`, `readOnly()`); `.subscribe()` reacts only to Reactive Forms' own Observables (`manualOverride.valueChanges`, `form.valueChanges`/`statusChanges`), which have no signal equivalent without `toSignal()`. This already matches the codebase's only other precedent (`main-lift-block-card.component.ts`, `display.component.ts` use `effect()` for signals only; `program-delete-button.component.ts`, `program-edit-toggle.component.ts` use `.subscribe()` only for one-shot dialog `afterClosed()`). Consolidating everything onto `effect()` was considered and rejected: the file's existing `toSignal(form.valueChanges...)` (`formValues`) is one aggregate signal over the whole form, so an `effect()` reading `formValues().manualOverride` would re-fire the enable/disable/reset side effect on *every* keystroke in *any* field, not just when `manualOverride` toggles — a real correctness regression, not just a style change. Doing it right would need a dedicated `toSignal(this.form.controls.manualOverride.valueChanges)`, adding wiring purely for idiom-uniformity with no behavior gain.

Landed as a general rule, written to `CONTEXT.md`'s Architecture conventions: prefer `computed()`/`effect()` for reacting to signal changes, especially UI/render side effects; prefer RxJS for stream-native logic — async orchestration, data transformations, combining/deriving multiple event sources; avoid `untracked()` — it opts out of the dependency tracking effects/computed exist to provide, so an agent reaching for it must ask for explicit sign-off and explain why no clean alternative worked. (Audited: `untracked()` has zero current uses in the codebase, so this is forward guidance only, nothing to retrofit.)

**2. Count of reactive registrations.** Leave the four separate (block-rehydrate `effect()`, manualOverride `subscribe()`, readOnly `effect()`, valueChanges/statusChanges `subscribe()`s) as-is — each reacts to a logically distinct trigger; merging would mix unrelated concerns into one callback, a worse smell than four small ones.

**3. Guard-then-branch repetition** (`onCreateProgram`/`onSelectProgram`/`onStatusTabChange` each calling `guardLeavingSession()` then branching). Leave as-is — only three call sites, each with a different body, and `onStatusTabChange` is documented as deliberately shaped differently (optimistic-set-then-revert, for `MatTabGroup` binding reasons). A shared wrapper would have to special-case that one anyway, for 2-4 lines saved per site.

**4. Deferred RxJS-pipeline rewrite of `guardLeavingSession()`/`confirmLeave()`.** Not adopted. `CanDeactivate` already accepts `Promise<boolean>` natively (not just `Observable<boolean>`), so "the guard could return an Observable" isn't a capability the current shape is missing. Wrapping the store's Promise-based `saveProgram()`/`cancelEditSession()` in `from(...)` would move the Promise/Observable adaptation from one clean `firstValueFrom()` call at the genuine RxJS boundary (`MatDialog`) out to the whole method — inverting which side adapts, for no gain.

**5. Ad hoc `notify()` calls** (`onDeleteProgram`, `onGenerate`, `saveProgram`). Leave as direct calls — each is a one-off "tell the user this action just succeeded" moment sitting in the handler that knows the outcome. Centralizing would require either the store taking on UI-toast concerns or an event-bus layer, both bigger than the problem.

**Doc placement note:** the new convention was added to `CONTEXT.md`'s existing "Architecture conventions" section (a bullet alongside the module-boundary/public-api rules already there) rather than as a new ADR. The `/domain-modeling` skill's guidance is that `CONTEXT.md` should stay a pure glossary and implementation conventions belong elsewhere — but this repo's `CONTEXT.md` already has an "Architecture conventions" section with implementation-flavored bullets (lint-enforced module boundaries, `InjectionToken`/`useExisting` wiring), so this follows existing precedent rather than the skill's ideal. Also considered and passed on: a dedicated ADR — the decision doesn't meet the "hard to reverse" bar (a style convention, cheap to revise later), even though it is somewhat surprising-without-context and the result of a real trade-off.
